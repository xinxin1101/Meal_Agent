# MealPilot 前端体验改版方案 v1.0

## 1. 改版目标

MealPilot 的前端不应像“参数输入 + JSON 结果”的开发演示，而应像一个可信、克制、易理解的个人膳食规划工作台。

本轮改版目标：

1. 用户进入页面后，10 秒内知道在哪里描述需求、在哪里生成计划。
2. 将健康档案、安全约束和本次规划条件分层，减少首次使用负担。
3. 让最终餐单成为视觉主角，Agent Trace 退居可展开的技术证据。
4. 把计划、协商、偏好记忆和聊天组织成同一条连续任务链。
5. 保留健康成年人边界、确定性验证、SSE、OCC 和记忆使用证据。

## 2. 现有页面主要问题

### 2.1 信息层级过于扁平

首页同时展示年龄、身高、体重、营养参数、时间、能量、蛋白质和过敏原。所有字段视觉权重接近，用户难以区分“必须先填”“可以稍后调整”和“安全上最重要”的内容。

### 2.2 主任务被技术信息干扰

SSE 连接状态、事件编号和 Agent Trace 与最终方案处于相近视觉层级。它们适合解释和排障，但不应比早餐、午餐、晚餐更醒目。

### 2.3 计划与聊天仍然相距较远

聊天在规划区域下方形成独立大模块。虽然接口已传入验证后的计划上下文，但视觉上仍像两个产品，用户不容易感知“正在围绕这份计划继续对话”。

### 2.4 结果的生活化表达不足

餐次当前主要展示名称和份量。缺少菜品摘要、用时、核心营养、适配原因、替代操作等信息，结果仍偏向求解器输出。

### 2.5 页面过长且首屏利用率不佳

大标题占据较多首屏空间，长表单继续向下延伸；用户生成计划后仍需在同一长页面中定位运行状态、结果和聊天。

### 2.6 样式系统逐阶段叠加

当前存在 `styles.css`、`phase2.css`、`phase3.css`、`phase4.css` 和 `phase5.css`。颜色、圆角、间距和组件命名来自不同阶段，后续维护容易继续产生局部补丁。

## 3. 设计方向

### 3.1 产品气质

关键词：`可信`、`清爽`、`温暖`、`有证据但不过度技术化`。

避免使用健身软件常见的强对比黑色、荧光绿和竞技感；也避免过多食物插画造成儿童化。建议以暖白、鼠尾草绿和少量杏色构成安静的工具型界面。

### 3.2 视觉语言

| 角色 | 建议 |
|---|---|
| 页面背景 | 暖灰白 `#F6F5F0` |
| 主色 | 深森林绿 `#1F5A45` |
| 主色浅底 | `#E7F1EA` |
| 强调色 | 杏橙 `#D8844A`，用于餐次和待确认状态 |
| 文字主色 | `#1E2D26` |
| 次级文字 | `#68756E` |
| 成功 | `#287A55` |
| 警告 | `#A66A20` |
| 错误 | `#B24A3B` |
| 卡片圆角 | 16px；大容器 20px |
| 阴影 | 低对比、短距离，仅用于浮层和主结果卡 |
| 中文字体 | 系统字体优先：`Inter, PingFang SC, Microsoft YaHei, sans-serif` |

颜色不能单独承担状态表达；状态同时使用图标、文字和形状。

## 4. 信息架构

桌面端采用轻量应用壳，而不是单页长落地页：

```text
┌──────────────────────────────────────────────────────────────┐
│ MealPilot        今日计划  对话助手  偏好与档案       用户入口 │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│ 页面标题 / 当前日期                         健康成年人适用说明 │
│                                                              │
│ 主要工作区                                             辅助栏  │
│                                                     当前档案摘要│
│                                                     记忆摘要   │
│                                                     数据版本   │
└──────────────────────────────────────────────────────────────┘
```

一级页面：

- **今日计划**：创建、运行、协商和查看一日餐单。
- **对话助手**：围绕当前已验证计划持续提问；没有计划时提供非医疗的一般饮食指导。
- **偏好与档案**：管理主动保存的偏好、健康成年人规划参数和明确过敏原。

移动端将顶部导航收敛为底部三项导航；安全说明保留在页面内容中，不采用遮挡内容的悬浮胶囊。

## 5. 今日计划页面

### 5.1 初始状态

首屏只突出一个自然语言需求框和明确的主按钮：

```text
┌─────────────────────────────────────┐
│ 今天想怎么吃？                       │
│ ┌─────────────────────────────────┐ │
│ │ 60分钟，高蛋白，1500–1700 kcal…  │ │
│ └─────────────────────────────────┘ │
│ [¥45] [60分钟] [90g蛋白质] [编辑]   │
│                                     │
│ 档案：26岁 · 减脂 · 轻度活动  [修改] │
│ 安全：过敏原未填写/已确认无过敏原    │
│                                     │
│                       [生成今日计划] │
└─────────────────────────────────────┘
```

交互规则：

- 自然语言解析后，将识别结果显示为可编辑的约束 Chip，而不是静默回填到远处表单。
- 时间、能量和蛋白质放入“本次目标”折叠面板。
- 年龄、身高、体重、活动水平和目标放入“档案摘要”，点击后使用右侧抽屉编辑。
- 过敏原单独作为安全区，不和普通口味偏好混排。
- 对“没有过敏原”使用明确选项：`已确认无已知过敏原`，不能通过空字符串推断安全。
- 主按钮只在健康成年人合同和必填字段通过校验后可用，并就地说明缺失项。

### 5.2 运行状态

提交后不清空整个页面，保留用户输入摘要，并将主区域切换为可理解的进度卡：

```text
正在生成今日计划                         预计几秒钟
● 理解需求  ━  ● 检索菜谱  ━  ◐ 组合方案  ━  ○ 安全复核  ━  ○ 完成
正在组合符合时间、能量和蛋白质要求的三餐

[展开技术详情]
```

- 默认显示用户语言：理解需求、检索菜谱、组合方案、安全复核、完成。
- SSE 状态、重连、事件编号和节点 payload 放在“技术详情”Disclosure 中。
- 断线重连使用非阻断提示；只有任务真正失败才显示错误操作。
- 进度动画遵守 `prefers-reduced-motion`。

### 5.3 完成状态

结果区采用“总览 → 三餐 → 验证证据 → 后续操作”的顺序：

```text
┌ 今日计划 ─────────────── 已通过安全与营养复核 ┐
│ 1623 kcal   148g 蛋白质   ¥25.05   56分钟      │
│ 能量目标  [█████████░] 1623 / 1500–1700       │
│ 蛋白目标  [██████████] 148 / ≥90               │
├───────────────────────────────────────────────┤
│ 早餐  燕麦鸡蛋早餐          约15分钟 · ¥6.20   │
│       1份 · 蛋白质…                  [查看]   │
│ 午餐  牛肉时蔬餐            约25分钟 · ¥12.40  │
│       2份                              [查看]   │
│ 晚餐  ……                                         │
├───────────────────────────────────────────────┤
│ 为什么这样安排？                                │
│ [询问助手] [调整条件重新规划] [保存/打印]        │
└───────────────────────────────────────────────┘
```

餐次卡第一版不依赖网络图片；使用稳定的餐次色块或本地抽象食材图形，避免第三方图片许可问题。等正式菜谱数据保存合规图片元数据后再增加封面图。

每张餐次卡建议展示：

- 中文菜名和餐次。
- 建议份量。
- 本餐能量、蛋白质和用时。
- 与用户显式偏好相关的标签。
- “查看做法/替代建议”入口。

后端若暂时没有单餐营养、价格、步骤和解释字段，前端不得自行估算，应显示已有信息或隐藏该项。

## 6. 无解协商设计

`PAUSED` 不作为普通错误页面，而是在原计划上下文中显示待确认卡：

```text
当前条件无法同时满足
安全约束没有被放宽。下面只列出已经由求解器验证可行的调整：

( ) 总时间从 35 分钟调整为 45 分钟
( ) 总时间从 40 分钟调整为 55 分钟
( ) 蛋白质目标从 120g 调整为 105g

[保持原条件]                         [采用调整并继续]
```

- 用差异格式展示“原值 → 新值”，避免只显示机器字段。
- 明确说明过敏原和忌口不会成为协商选项。
- 409 冲突使用页内通知，并自动刷新选项；不让用户理解 OCC 技术术语。
- 恢复后沿用同一个计划页面、Run 和进度条。

## 7. 对话与记忆设计

### 7.1 对话助手页面

对话作为一级页面，但右上方持续展示当前上下文：

```text
正在讨论：今日计划 · 1623 kcal · 已验证       [查看计划]
使用偏好：清淡少油、喜欢牛肉                 [管理]
```

- 助手回复顶部使用低干扰来源标签：`模型生成` 或 `本地可靠回复`。
- `memories_used` 默认显示为一行证据摘要，可展开查看具体内容。
- 没有当前计划时清楚显示“本次回复未关联已验证计划”。
- 提供围绕当前计划的快捷问题：`午餐可以换什么？`、`如何提前备餐？`、`减少最近吃过的菜`。
- 涉及调整计划约束的对话不能直接篡改已验证计划，应生成“带入规划”的操作，并重新走 Solver 和验证。

### 7.2 偏好与档案页面

将“长期偏好”和“安全档案”严格分区：

- 长期偏好：口味、主动忌口和烹饪风格。
- 规划档案：年龄、营养计算参数、身高、体重、活动水平、目标。
- 安全信息：过敏原，由用户明确填写或明确确认没有已知过敏原。

界面始终提示：不从行为推断过敏、疾病或健康状态。删除个人档案、清空偏好和删除历史规划应是不同操作，避免误解。

## 9. 状态设计

每个主要区域都必须定义以下状态：

| 状态 | 用户体验 |
|---|---|
| 初始 | 示例提示、可执行主操作，不展示空白大卡片 |
| 加载 | 保留布局，使用骨架或明确进度文案 |
| 成功 | 突出结果和下一步，不突出事件编号 |
| 暂停 | 显示可行协商选项及原值/新值 |
| 空数据 | 解释为什么为空，并给出创建入口 |
| 网络断开 | 非阻断重连提示，并说明正在同步最新状态 |
| 422 | 将错误映射回具体表单字段 |
| 409 | 自动刷新并说明数据已更新 |
| 失败 | 提供保留输入后重试或调整约束的路径 |

## 10. 响应式与无障碍

- 断点建议：`<640px` 手机、`640–1023px` 平板、`≥1024px` 桌面。
- 手机端表单字段单列；主操作可在视口底部形成安全的粘性操作区。
- 所有可点击区域至少 44×44px。
- 文字和背景满足 WCAG AA 对比度。
- 表单错误通过 `aria-describedby` 关联字段。
- Drawer 和 Dialog 必须锁定焦点、支持 Escape、关闭后恢复焦点。
- SSE 状态用克制的 `aria-live=polite`；避免每个节点变化都打断屏幕阅读器。
- 图表同时提供文本数值，不能只靠颜色或长度表达。
- 支持 200% 字体缩放和键盘完整操作。

## 11. 数据合同补充需求

为了完整实现结果卡，建议后端后续补充或确认以下只读字段；未提供前不阻塞页面骨架改版：

- 菜谱中文展示名由后端/数据集返回，移除前端硬编码 `recipeNames`。
- 每餐营养和准备时间拆分值。
- 菜谱步骤摘要、主要食材和原始用量。
- 与本次请求匹配的显式标签或证据引用。
- 合规图片元数据；没有授权图片时返回空值。
- 计划创建时间、数据版本和价格快照的用户可读摘要。

所有数值仍由后端 Decimal 权威结果提供，前端只负责格式化展示。

## 12. 分阶段实施计划

### UI-R1：设计系统与应用壳

- 合并阶段性 CSS，建立颜色、字号、间距、圆角和阴影 Token。
- 创建顶部导航、页面容器和三个一级页面骨架。
- 保持现有 API、SSE 和状态逻辑不变。

完成标准：桌面和 390px 手机端导航清晰，无横向滚动；现有功能入口没有丢失。

### UI-R2：规划输入重构

- 实现自然语言主输入、约束 Chip、档案摘要和档案编辑抽屉。
- 将过敏原提升为独立安全区。
- 422 错误映射到字段。

完成标准：默认首屏不再展示超长表单，用户仍可访问和修改全部合同字段。

### UI-R3：运行与结果重构

- 重做用户语言进度条，将技术 Trace 折叠。
- 实现计划总览、目标达成条、三餐卡和验证徽章。
- 保留重连和 Run Snapshot 回退逻辑。

完成标准：完成态首屏首先看到三餐和关键指标；没有 JSON 或内部 recipe id 作为主文案。

### UI-R4：协商、聊天和记忆闭环

- 重做差异化协商卡。
- 将聊天提升为一级页面，持续显示当前计划上下文。
- 将偏好与健康档案分区，并保留 `memories_used` 和 `response_source` 证据。

完成标准：从结果进入对话后能明确知道正在讨论哪份计划；聊天调整可重新进入规划流程。

### UI-R5：质量验证

- 增加关键组件测试和完整用户路径测试。
- 验证 SSE、PAUSED/恢复、409、422、模型降级、空记忆和删除记忆。
- 验证 Docker/Nginx、刷新、移动端、键盘和降低动画偏好。

完成标准：`pnpm run build`、前端测试、后端回归测试和 Docker 演示闭环全部通过。

## 13. 本轮明确不做

- 不改变 Solver、验证规则或 Agent 权限。
- 不增加疾病饮食、医疗建议、周计划或家庭多人计划。
- 不为了美观伪造菜谱图片、营养值、食材克数或制作步骤。
- 不引入网络图片作为未审核菜谱的默认封面。
- 不把 Agent 隐藏推理展示给用户；只展示安全事件和验证证据。
- 不在本轮接入刚建立的爬虫 Skill。

## 14. 推荐实施顺序

建议严格按照 `UI-R1 → UI-R2 → UI-R3 → UI-R4 → UI-R5` 实施。第一轮只做应用壳和设计 Token，不同时改动业务 API；第二轮再重构规划输入。这样每阶段都能独立构建、验收和回退。
