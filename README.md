# MealPilot

Constraint-aware, non-medical meal planning for healthy adults.

This repository delivers the frozen local MVP: a one-person day plan from versioned local, Solver-eligible recipes and nutrition fixtures, with a structured coverage/infeasibility result. It runs on Python 3.11 and the deterministic core does not require an LLM or vector database. Contract v2 has no price, budget, or structured equipment planning.

## Quick start

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/bootstrap.ps1
powershell -ExecutionPolicy Bypass -File ./scripts/test.ps1
powershell -ExecutionPolicy Bypass -File ./scripts/start.ps1
```

Open `http://127.0.0.1:5173` for the demo UI or `http://127.0.0.1:8000/docs` for the API. Stop both local services with:

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/stop.ps1
```

The first page now requires account registration or login. User IDs are generated by the backend; the browser cannot choose another user's identity. Local development persists a generated signing secret under `.runtime`. Production requires `MEALPILOT_AUTH_SECRET` (at least 32 characters), HTTPS, and Secure cookies. The profile page supports complete account-data export and permanent account deletion.

For the demo UI, run `pnpm install` then `pnpm dev` inside `frontend`, or run `docker compose up --build -d` and open `http://127.0.0.1:8080`. See [`docs/deployment.md`](docs/deployment.md) for health checks, SSE proxy behaviour, durable-volume handling, and registry troubleshooting.

Recipe acquisition is not required for infrastructure startup, but planning remains business-blocked until the formal catalog has Solver-ready breakfast, lunch, and dinner coverage. The administrator can preview and queue a bounded personal-study job; a separate Worker performs network work and writes only to the persistent raw/review boundary. Personal study alone never authorizes publication. See [`docs/recipe_automation.md`](docs/recipe_automation.md).

The runtime catalog starts without repository sample recipes. Samples remain test fixtures and are enabled only with `MEALPILOT_INCLUDE_SAMPLE_RECIPES=true`. New captures follow `initial validation -> bounded LLM display structuring -> Pydantic/deterministic final validation -> administrator batch approval and publication`. The active UI no longer asks administrators to register licence evidence. Source URL/hash/time remain stored, and published records are scoped to this internal personal-study application rather than public redistribution.

`POST /v1/meal-plans/deterministic` accepts a complete healthy-adult profile and time/energy/protein constraints. It materializes planning inputs from the local nutrition catalog, then performs safety and Solver-eligibility filtering, candidate coverage checks, CP-SAT selection, and Decimal revalidation.

Ingredient amounts preserve explicit grams when available and otherwise use the reviewed qualitative labels `适量` or `少许`. Qualitative quantities never receive guessed grams; recipes without authoritative per-serving nutrition remain cooking references and cannot enter the Solver.

`POST /v1/agent-runs` runs the M2 LangGraph orchestrator: it extracts supported numeric observations from a query, performs local BM25 retrieval, invokes the deterministic planner, and emits a safe structured trace.

`POST /v1/runs` is the single durable runtime. Supply `Idempotency-Key`; it creates a persisted run and returns `202`. Use `GET /v1/runs/{run_id}` for its authoritative snapshot, `GET /v1/runs/{run_id}/events` for SSE replay (`Last-Event-ID` is supported), and `GET /v1/runs/{run_id}/audit` for a redacted operational summary. An infeasible run can become `PAUSED`; submit a server-issued option to `/decisions` with `expected_run_version`, or cancel a non-terminal run through `/cancel`. Stale writes return HTTP 409. The obsolete in-memory `/v1/negotiation-runs` path has been removed.

`POST /v1/nutrition-target-suggestion` returns an advisory, versioned healthy-adult estimate from a complete profile. It never changes planning constraints automatically: the frontend requires the user to press “确认并应用到本次目标”. The estimate is not medical advice and still requires qualified domain approval before a real-user beta.

## SiliconFlow configuration

Copy [`.env.example`](.env.example) to `.env` and set `SILICONFLOW_API_KEY` and `SILICONFLOW_MODEL` when ready. The adapter uses SiliconFlow's OpenAI-compatible base URL, `https://api.siliconflow.cn/v1`.

In the frontend, **解析并回填约束** calls `POST /v1/constraint-suggestions`. It sends only the free-text request and returns explicit budget, time, protein, and energy numbers for the user to review before submitting. The model never receives the health profile or recipe corpus; it cannot select recipes, relax safety rules, or change the CP-SAT/Decimal-validated plan. If the service is unavailable or returns invalid data, the endpoint falls back to the local deterministic extractor.

## Layout

- `docs/`: product, data, solver, safety, and acceptance contracts.
- `backend/`: API and M1 deterministic domain modules.
- `frontend/`: reserved React/Vite application shell for M5.
- `tests/`: deterministic contract and fixture tests.
- `data/`: local, versioned development fixtures only.
